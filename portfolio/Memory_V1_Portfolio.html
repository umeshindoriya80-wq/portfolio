Memory for Spotter · V1 Case Study · ThoughtSpot

We didn't invent business context.
We made it dynamic.

Analysts could always add context manually. What changed: AI could now build it — and update it over time from chat, documents, and other signals. That is why we called it Memory, not static context.

ROLE

TIMELINE

SCOPE

SPEAKER NOTES

Analysts in ThoughtSpot could always add context to their data models — instructions, definitions, rules. What the PM discovered through testing was different: AI could now build that context for you, and update it over time as more signals came in — from chat, documents, other sources. That is why we called it Memory instead of static context. Static context sits there. Memory evolves. V1 made one deliberate constraint: create memory from Liveboards, and let Spotter use chat signals to correct existing memory — but no active memory addition via chat yet. If Spotter can freely learn from anything you say, you need to be very confident it saves the right thing. We were not confident enough yet.

The Problem

The analyst is the bottleneck — manual, scattered, going stale.

REPETITIVE MANUAL WORK

Write instructions. Create reference questions one by one. Update when the business changes. Delete stale entries. Repeat — across every data model they own.

NO SINGLE VIEW

If Spotter answers wrong, the analyst checks all four surfaces to find the gap. No single place to look.

COLD-START PARALYSIS

When enabling Spotter on a new data model, analysts think: "I don't know what to add." So they don't enable it at all.

SPEAKER NOTES

Spotter is fully capable of using business context — definitions, conventions, rules. The problem is upstream. That knowledge lives in people's heads, documents, dashboards — and the only way it reaches Spotter is if the analyst manually converts it, one entry at a time across four separate surfaces. Three specific pains: the work is repetitive and goes stale, there is no single view when something breaks, and the cold-start problem means many analysts never even start. Memory doesn't make Spotter smarter — it removes the bottleneck.
The Concept

One Memory. Every source. Spotter reads from one place.

Every existing surface — and the new sources — converge into a single Memory that resolves conflicts and updates over time.

Liveboards and chat are new: bulk context creation from objects the business already trusts, instead of manual entry.

The analyst manages one place. Spotter consumes one place. The bottleneck is gone.

SPEAKER NOTES

This is the conceptual shift Memory makes. All existing context surfaces — instructions, column descriptions, reference questions, business terms — plus the new sources converge into a single Memory that resolves conflicts and updates over time. If knowledge changes, memory updates; old and new no longer coexist silently. Liveboards and chat are the new sources: bulk creation from objects the business already trusts. The analyst manages one place, Spotter consumes one place. The bottleneck from the problem slide is gone. Where does memory come from first, and how do we keep it trustworthy? WHAT WE LEARNED — TYPES OF MEMORY
Chat context — memory within a single conversation, lost when the chat ends
Short-term memory — persists for a session or a few chats, then fades
Long-term memory — persists indefinitely; analyst-managed or AI-saved facts
Memory across chats — knowledge that carries across separate conversations
"Dreaming" — passive background learning from conversations, without explicit user action. The AI is always listening and forming patterns.

SPEAKER NOTES

We started with consumer AI products — ChatGPT, Claude, OpenAI Live, Copilot, MongoDB, Gemini. The goal was to understand the full vocabulary of what memory can be. We found five types: chat context (gone when the conversation ends), short-term memory (a session or two), long-term memory (persists), memory across chats (carries over), and what we started calling "dreaming" — passive background learning from conversations. The AI is updating its understanding without the user explicitly telling it anything. This last type was the most interesting — and the most dangerous to introduce without visibility. That insight became central to V1's constraints and V2's entire problem statement.

SPEAKER NOTES

The second layer of research: enterprise AI products — Tableau AI, Cursor, OpenAI Enterprise, Intercom Fin. Here we were looking at levels, not types. We found a spectrum: user-level memory (scoped to one person), across-user memory (shared by a team), data-model-level memory (tied to a specific dataset), across-data-model memory (shared context), and enterprise memory (org-wide, admin-governed). The insight: every product we studied solved user-level or org-level. Nobody had ThoughtSpot's problem — an analyst who owns AI accuracy across an entire team's data models. The data model layer was ours to define. That gap in existing solutions is what made the IA work genuinely new rather than an adaptation of a known pattern.

We mapped 7 memory types across 14 dimensions — risk, persistence, visibility, ownership — to find what could be simplified.

Evaluated two structures: OP1 Distributed (each object owns its memory — clear ownership, but analysts repeat updates across every data model) vs OP2 Unified (one central layer — one place to manage, scales across models).

Landed on two levels — Central + Personal — with tagging instead of extra tiers. Simpler to manage, simpler to scale.

MY ROLE — IA led purely by me. PM provided resources and working sessions; stakeholders pressure-tested through multiple feedback rounds.

SPEAKER NOTES

With the research done, we had to decide our own IA. First proposal had three levels — Central, Data Model, Personal. I built a components table mapping seven memory types across fourteen dimensions and evaluated two structures: distributed (clear ownership, but repeated updates across models) vs unified (one pane of glass, but cognitive overload risk). We took a middle path: two levels, one management surface, with tagging for specificity. That decision is now being tested by agent-level memory and tool calls — and the flat-tagged model is holding.
Decision 1 of 2 — Where does memory come from?

We chose verified knowledge over easy knowledge.

Both were exciting. Both were important. Chat: type it, done — power in the analyst's hands. Liveboard: upload a board, memory in bulk. With limited engineering bandwidth, we could only sequence — not ship both. That made the prioritization call critical.

💬

Option A — Chat memory

RISK: EARLY TRUST FAILURE
  • ✓ Big announce-able feature
  • ✓ Power right in the analyst's hands
  • ✕ AI misinterprets — user means one thing, agent saves another
  • ✕ No review step. A wrong save shapes org-wide answers.
  • ✕ Doesn't solve cold start — still requires analyst to know what to type
✓ CHOSEN FOR V1
📊

Option B — Liveboard memory

UNBLOCKS THE MOST USERS
  • ✓ Solves cold start — analyst already has Liveboards, no blank slate
  • ✓ Bulk: 1–2 actions, memory across an entire data model
  • ✓ Analyst-curated, already verified, org already trusts them
  • ✓ Review & edit before anything saves — control before automation
  • ✕ Slower to implement · doesn't help analysts without Liveboards
THE CALL — For analysts already with Spotter, adoption of Spotter matters more than adding new data models. Liveboard unblocks the most of them, with the least risk.

SPEAKER NOTES

Once we had the architecture, we had to decide where memory comes from first. The tempting answer was conversation — fast, easy. But the risk: a user says one thing, Spotter saves something slightly different, and the analyst has no idea. In an early-stage AI product that trust failure is very hard to recover from. As a team we chose Liveboards: analyst-curated, verified, already trusted. It solved the cold-start problem — organizations already have hundreds of Liveboards full of verified business meaning — without the quality risk of unverified conversational content. Chat was limited to corrections of existing memory, not free addition.

Choosing Liveboard as the first memory source was the strategic decision. But that decision immediately opened three execution problems. First: what is the UX flow for adding a Liveboard to memory — how many steps, what choices does the analyst make, how does it feel? Second: where in the platform does memory management live? This had to be scalable — a place that could hold memory for all agents, all data models, future sources we hadn't built yet. Third: how do analysts get to that place? We had to create entry points across the product so adding memory is never more than two clicks away from wherever they are.
Decision 2 of 2 — Where does memory live?

One new page. One touchpoint. Analyst lands in Spotter prepared.

Memory sits at the central layer — so we created one page to manage it: "Spotter Memory", with the Memory Sources tab.

From the data management page, a single "Add memory" link. Any memory added from anywhere lands in the same place — where the analyst can add Liveboards across multiple data models at once.

Then they go to Spotter — already prepared.

WHY ONE PAGE — With multiple agents (Spotter, Spotter Model, Spotter Viz), memory had to live centrally, not inside any single agent's surface — that's what made it scalable.

SPEAKER NOTES

The second decision: where does memory management live? Since memory sits at the central layer — shared across data models and across agents — it needed one home, not a corner of any single agent's settings. At the time we had multiple agents: Spotter, Spotter Model, Spotter Viz. So we created the Spotter Memory page with the Memory Sources tab inside the data workspace. The flow: the analyst is in the data management page, sees a single "Add memory" link, lands on Memory Sources, and can add Liveboards across multiple data models in one go. Adding memory from anywhere in the product lands in this same place. One new page, one touchpoint — and the analyst goes to Spotter already prepared. This central placement is also what made the architecture survive later changes, like the move toward one merged Spotter agent.
The Craft — Four Hard Design Problems

The flow had to be guided, not a form. Here's why.

01
Finding the right Liveboard

Analysts can access hundreds of Liveboards — not all of them are good memory sources. We had to surface the right signals: verified status, ownership, relevance to the data model. Without this, analysts would pick at random and generate poor memory.

→ Designed: verified badges, filtered views, ownership signals
02
Capped at 3 Liveboards per add

A Liveboard generates bulk memory. Letting analysts add 10 at once would overload the review step and risk exceeding cluster capacity. The cap made the flow reviewable and kept generation manageable — analysts could always add more in a second pass.

→ Constraint made the flow feel intentional, not limited
03
Context step + data model scoping

We iterated significantly on this step. The context field needed to be prominent — richer analyst input = better AI output. Data model selection defaulted to all, but analysts had to knowingly see which models they were scoping memory to. We tried multiple layouts before landing on the right hierarchy.

→ Iterated: big prompt field, explicit model list, all selected by default
04
The loading state problem

Memory generation takes time — and it's a 0-to-1 process, not a progress bar. The analyst had to wait with no feedback. We went through many iterations: full-page loading, inline toast, background generation with notification. Landed on: submit → toast → notification with "View" when ready.

→ Final: non-blocking generation + notification on completion

SPEAKER NOTES

Four specific design problems inside the Liveboard memory flow. First: with hundreds of accessible Liveboards, we had to give analysts the right signals to pick the right one — verified status, ownership, relevance. Second: capped additions at 3 per session. A Liveboard generates bulk memory — 10 at once would have made the review step overwhelming and risked cluster capacity. Third: the context + data model step went through many iterations. We wanted the context field to be prominent because richer input means better memory. And analysts needed to see exactly which data models they were scoping memory to — knowingly, not as a side effect. Fourth: generation time. It's not a loading bar — memory is being created from scratch, which takes real time. We landed on a non-blocking flow: submit, toast confirmation, then a notification with a View action when memory is ready. Don't make the analyst wait at a spinner.

What It Left Unsolved

We introduced learning from conversation.
We just didn't make it visible enough.

V1 shipped Liveboard memory, a Memory Sources page — and passive learning from chat, introduced quietly. No notification. No indication anything was being saved.

Feedback was immediate: "Before you give us more ways to add memory, show us what's already there."

And analysts who missed the Liveboard flow might never find Memory Sources. But nobody misses the Spotter chat. That became the foundation for V2.

SPEAKER NOTES

V1 shipped three things: Memory from Liveboard, passive chat learning, and the Memory Sources page. We made a mistake with the conversation learning — we introduced it quietly. The thinking was it would feel seamless. The reality was it felt invisible. The next planned project was active memory creation from conversation — but user feedback redirected us: before more ways to add, show us what is already there. Transparency first, then creation. And a reach problem: the Memory Sources page sits in the data workspace; analysts who miss the Liveboard flow may never find it. But every analyst uses Spotter chat. That insight — Spotter is where analysts live — became the strategic foundation for V2.
Reflection

Three things V1 taught me about designing AI systems.

01
Knowledge systems ≠ configuration systems.

Configuration stays static. Knowledge must evolve. That distinction shaped every architectural decision we made.

02
Trust beats capability in early AI products.

We chose the slower, constrained path of Liveboard-sourced memory specifically to protect trust. That was the right call.

03
A scalable IA outlives its first workflow.

The Personal + Central structure is being tested by platform changes we didn't anticipate — agent-level memory, tool calls. Early signal: it's holding.

SPEAKER NOTES

First — knowledge systems are fundamentally different from configuration systems. Configuration stays static; knowledge has to evolve. Second — trust matters more than capability in early AI products. We deliberately chose the slower path of Liveboard-sourced memory over conversational memory to protect trust. Third — a scalable information architecture often matters more than the first workflow you build on it. We debated a data-model-level tier; we kept it flat — two levels with tagging. As the platform evolves toward agent-level memory and tool calls, the question is no longer where memory lives but how it's tagged and fetched. Early signal is that the flat structure was the right call.
